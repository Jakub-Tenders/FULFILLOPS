# ADR-001: Initial FulfillOps architecture

- **Status:** Proposed
- **Date:** 2026-11-10

## Context

FulfillOps must accept orders quickly, reserve inventory exactly once under
concurrent requests, and complete accepted orders asynchronously. The order,
inventory, idempotency mapping, and work item must survive API and worker
restarts.

## Decision

We will implement the application in Python using FastAPI, PostgreSQL, and a
separate worker process. PostgreSQL will provide both the durable business data
and a transactional work table/outbox. The API will create the order, reserve
inventory, record the idempotency mapping, and enqueue the work item in one
database transaction.

The worker will claim pending work transactionally, process it with bounded
retries, and retain permanently failed work for operator review. Database
constraints and row-level locks, rather than process-local state, will enforce
the inventory and idempotency invariants.

## Invariants

1. `inventory.available` is never negative.
2. One idempotency key maps to at most one order.
3. A reused key with a different normalized payload is rejected.
4. An accepted order is not lost when an API or worker process restarts.
5. Worker retries cannot apply the business completion effect twice.

## Consequences

PostgreSQL is required for local development and deployment. The design is
simple to reproduce with Docker Compose and can be deployed with two API and
two worker replicas. At-least-once work delivery requires an explicit claim,
retry, and completion state machine; exact-once business behavior is enforced
by persisted order state and guarded transitions.
